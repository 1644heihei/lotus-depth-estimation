# タイル分割推論 — 実施結果（不採用）

実施: 2026-08-27
ブランチ: `feature/object-depth-aux-loss`
計画: [`tiled_inference_plan.md`](tiled_inference_plan.md) / 前提: [`phase0_findings.md`](phase0_findings.md)

**結論: タイル分割推論は NYUv2 では成立しない。全設定でベースラインを下回った。**
計画では T0〜T3 に 2 日を見込んでいたが、対照実験を最初から組み込んだため **1 時間で決着**した。

---

## 0. 要約

| 発見 | 数値 | 帰結 |
|------|------|------|
| タイル融合は全設定でベースライン以下 | 最良でも **+0.09%**（n=60、実質ゼロ） | **不採用** |
| 手法の最適設定は自身の no-op | σ→0 で利得がゼロに漸近 | 転写する情報量を増やすほど悪化 |
| **切り出すだけで −22.8%** | 同 latent 密度の対照 C2（654枚） | **視野の喪失＝文脈の喪失**が主因 |
| crop に latent 密度を足すほど悪化 | 1.00x −22.8% → 1.75x −39.3% | 全画像とは**逆**の挙動 |
| 勝率は 4〜8% | 654枚中 90% 以上で悪化 | ばらつきではなく系統的な劣化 |

**最大の含意: 512→768 の利得は「latent 容量が増えたから」ではなく
「768 が Lotus の適正動作点だから」だった。**

## 1. 実装

| パス | 内容 |
|------|------|
| `utils/tiled_depth_fusion.py` | タイル幾何 / アフィン整合 / フェザー重み / F1・F2 融合 |
| `eval_tiled_depth_nyuv2.py` | 評価ドライバ（アブレーションフラグ付き、タイル予測をキャッシュ） |

### 実装の検証（単体テスト）

融合ロジックが正しいことを、負の結果を報告する前に確認した:

| テスト | 結果 |
|--------|------|
| タイル被覆の完全性（grid 1〜3 × overlap 0〜0.35） | 全設定で画像を過不足なく被覆、重み最小値 1.0 |
| `fit_affine` の係数回復 | a=0.3700（真値 0.37）/ b=0.1200（真値 0.12） |
| 恒等性（タイル＝全体パスなら出力＝全体パス） | **F2 で厳密に 0**、F1 で 6e-08 |
| アフィン不変性（タイルごとに任意の scale/shift） | 両方式とも 1.8e-07 |
| 不正タイクへの頑健性（1 枚に傾きを注入） | F1 誤差 0.333 に対し **F2 は 0.0119（28 倍頑健）** |

F2（周波数分離）は**差分ベース**で定式化した:

```
D = global + Σ w_i · highpass(aligned_i − global[tile_i]) / Σ w_i
```

タイル自体ではなく「タイルと全体パスの差分」の高周波だけを転写する。
捨てる低域がまさに「信用しない構造の不一致」であり、
かつ**タイルが全体パスと一致すれば寄与が厳密に 0** になる（当初の
「タイルを直接ぼかす」実装ではゼロ埋めキャンバスの外側が滲み込み、恒等性が
2e-02 ずれていた）。

## 2. 結果

比較基準は **公式 Lotus `processing_res=768` の abs_rel 0.05000**
（512 の 0.05543 と比較すると、設定ミス修正分の 9.8% を手法の手柄に誤算入してしまう）。

### 2.1 融合戦略と σ のスイープ（n=60、grid 2×2 / overlap 0.25 / tile_res 768）

| 融合 | σ | abs_rel | gain | 勝率 |
|------|---|---------|------|------|
| none（全体パスのみ） | — | 0.08754 | — | — |
| **F1（タイル全体を加重平均）** | — | 0.11039 | **−26.1%** | 15.0% |
| F2 | 32 | 0.09767 | −11.58% | 28.3% |
| F2 | 8 | 0.08855 | −1.16% | 33.3% |
| F2 | 2 | 0.08757 | −0.04% | 48.3% |
| F2 | 1 | 0.08750 | +0.04% | 45.0% |
| **F2** | **0.5** | **0.08746** | **+0.09%** | 68.3% |

σ を下げるほど（＝転写する情報を減らすほど）良くなり、**σ→0 で利得がゼロに漸近する。
すなわち本手法の最適設定は「何も転写しない」状態**であり、+0.09% はノイズの範囲。

### 2.2 対照実験 C2 — 利得の由来の切り分け（654枚、F1）

「タイル分割の効果は解像度由来か、切り出し由来か」を分離するため、
**latent 密度が全体パスと等しくなる** `tile_res` でも測定した
（tile 366px / global 640px なので 768 × 366/640 ≈ 440）。

| 設定 | latent 密度 | abs_rel | gain | 勝率 |
|------|-------------|---------|------|------|
| 全体パスのみ | 1.00x | **0.05000** | — | — |
| grid 2, tile_res **440** | **1.00x** | 0.06142 | **−22.8%** | 8.0% |
| grid 2, tile_res 768 | 1.75x | 0.06964 | **−39.3%** | 4.4% |

n=60 での追加測定（F1）:

| 設定 | latent 密度 | gain |
|------|-------------|------|
| grid 2, tile_res 1024 | 2.33x | −65.7% |
| grid 3, tile_res 768 | 2.50x | −41.5% |

## 3. 解釈

### 3.1 独立した 2 つの負の効果

**(a) 切り出すだけで −22.8%（文脈の喪失）**

C2 は latent 密度が全体パスと同一で、違いは**視野だけ**。それでも 22.8% 悪化する。
単眼深度推定は消失点・接地面・物体サイズ事前分布といった**シーン全体の文脈**に依存する。
366×274 の crop には部屋の構造が写っておらず、モデルは手がかりを失う。

**(b) crop に latent 密度を足すほど悪化する**

1.00x で −22.8%、1.75x で −39.3%、2.33x で −65.7%。
**全画像で観測された挙動（512→768 で +9.8%）と正反対**である。

### 3.2 「latent 容量」ではなく「適正動作点」だった

(b) と、Phase 0 で観測された「全画像 1024 で −14.4%」は同じ説明で一貫する:

> **Lotus には適正な入力解像度（768 付近）があり、そこから離れると
> 上下どちらの方向でも劣化する。**

`processing_res` は最大辺基準なので、366px の crop を tile_res=768 で処理すると
**2.1 倍に拡大**され、1024 なら 2.8 倍になる。学習時に見たことのない
拡大率の入力になり、破綻する。全体パスが 640→768（1.2 倍）で済むのとは事情が違う。

タイル分割は「crop する」と「拡大する」の**両方**を必要とするため、
この前提の下では原理的に成立しない。

### 3.3 計画の前提が誤っていた

[`tiled_inference_plan.md`](tiled_inference_plan.md) §1 は
「モデルが得意な解像度を保ったまま 1 画素あたりの latent 容量を増やせる」
ことを前提にしていた。**`processing_res` が最大辺基準である以上、
crop の latent 容量を増やすことと拡大率を上げることは同じ操作であり、分離できない。**

同計画は既に一度、根拠（境界がボケる → 解像度で改善）を
[`phase0_findings.md`](phase0_findings.md) §3.5 の空間分解で訂正していたが、
残った根拠も本測定で否定された。

---

## 4. 結論と次の含意

**NYUv2 においては、公式 Lotus `processing_res=768`（abs_rel 0.05000）が
学習なし手法の実質的な上限である。**

これを超えるには:

| 方向 | 根拠 |
|------|------|
| **高解像度データセット** | NYUv2 は 640×480 で、768 は既に拡大。原画像に無い情報は生まれない。<br>DIODE / ETH3D は**本リポジトリが既に対応済み**（`datasets/eval/depth/configs/`）で<br>Lotus の標準ベンチマークでもある |
| **学習を伴う別アプローチ** | ただし fine-tune 税（9%+）を構造的に回避する設計が必須<br>（凍結 UNet + zero-init 側枝、[`lotus_improvement_plan.md`](lotus_improvement_plan.md) Phase 2-1） |
| **タスク自体の変更** | 法線推定は指標に alignment が無く、クラス→向きの事前分布が強い（別途検討） |

物体検出をタイル配置のガイドに使う Stage 2（計画 §6）は、
**タイル分割そのものが成立しないため実施しない。**

## 6. 教訓

1. **対照実験を最初から回すと撤退が速い。** C2（同 latent 密度）を本測定と同時に
   設計していたため、「効かない」だけでなく**「なぜ効かないか」**が同時に判明した。
   2 日の計画が 1 時間で終わった。
2. **負の結果を報告する前に実装の正しさを検証する。** 恒等性・アフィン不変性・
   頑健性の単体テストを先に通したので、「バグで悪化したのでは」を排除できた。
   実際、初期実装には恒等性が崩れるバグ（ゼロ埋めキャンバスのぼかし）があり、
   テストが無ければ気付かなかった。
3. **設定の意味を確認する。** `processing_res` が最大辺基準だと理解していれば、
   「crop の latent 容量を上げる」と「拡大率を上げる」が同一操作であることは
   実装前に分かったはずだった。
