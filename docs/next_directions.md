# 次の研究方向 — 候補の整理

作成: 2026-08-28
ブランチ: `feature/object-depth-aux-loss`

深度 × 物体条件付けの路線が終了したため、次の方向の候補を比較する。

---

## 前提: なぜ従来路線が終わったか

| 実測 | 数値 |
|------|------|
| 数ヶ月分の物体条件付け実験の最良値 | 公式 Lotus と差 **0.09%**（＝誤差） |
| 完璧な regressor があった場合の上限 | **2.1%**（判定閾値 5% 未満） |
| 誤差の空間分布 | 物体/背景・境界/内部いずれも**密度ほぼ 1.0（均等）** |
| タイル分割推論 | 全設定で **−22.8 〜 −65.7%** |
| 設定ミス修正（512→768） | **+9.8%**（学習なし。これが唯一の改善） |

詳細: [`phase0_findings.md`](phase0_findings.md) / [`tiled_inference_results.md`](tiled_inference_results.md)

**共通の失敗原因は 3 つ:**

1. **指標が注入した量を洗い流す** — depth は least-square alignment で絶対値が消える
2. **誤差が集中していない** — 攻めどころが存在しない
3. **注入情報がモデル本体より不正確** — regressor abs_rel 0.374 vs Lotus 0.055

**新しい方向は、この 3 つのどれかを構造的に回避していなければならない。**

## 候補の比較

| 案 | 測定可能性 | 事前分布の強さ | データ障壁 | 上記のどれを回避するか |
|----|-----------|---------------|-----------|----------------------|
| **A. 法線推定** | ◎ alignment 無し | ○ クラス→向きは強い | 中（法線 GT 未取得） | **①②③** |
| **B. 鏡 × Mirror3D** | △ 補正 GT が必須 | ◎ 幾何的制約 | 大（Mirror3D 入手） | **②③** |
| **C. 鏡セグメンテーション** | ◎ IoU / F値 | ◎ | 中（MSD / PMD） | **①②③**（タスクごと変更） |
| **D. 高解像度データ** | ◎ 標準スイート | — | 中（DIODE / ETH3D） | ②（原画像に情報がある） |
| **E. 凍結 UNet + zero-init 側枝** | ◎ | — | 小 | 何も回避しない（**上限 19% のまま**） |

---

## A. 法線推定への転換

- **指標に alignment が一切ない**（`evaluation/util/normal_utils.py` は角度誤差のみ）
  → depth で致命的だった原因①が消える
- **クラスは「距離」をほとんど制約しないが「面の向き」は強く制約する**
  （テーブル天板は必ず水平、壁は必ず垂直）→ 原因③が反転しうる
- 法線推定が苦手なのは**テクスチャの無い平面**で、検出物体が覆う領域と重なる
  → 原因②も変わる可能性（要測定）
- リポジトリは既に対応済み: `train_lotus_g.py` / `LotusGPipeline` / `evaluation/dataset_normal/`
- 公式重み: `jingheya/lotus-normal-g-v1-1` / `-d-v1-1`
- **障壁**: `datasets/eval/normal/` が空。法線 GT の取得が必要
- **注意**: `LotusGPipeline.default_processing_resolution = 768` も同じ。設定ミスの罠は同様

## B. 鏡を平面として推定（Mirror3D の補正 GT を使用）

- **誤差が病的に集中する初めてのケース** — モデルは反射像の奥行きを自信を持って誤る
- 「鏡 → 平面」は統計的事前分布ではなく**幾何的制約**
- **決定的な障壁**: NYUv2 の鏡領域は Kinect の IR が鏡面反射するため **GT が穴**。
  `evaluation/evaluation.py:105` が `depth_raw_linear` を使うため、
  **標準ベンチマークでは鏡画素は採点されない**（実測確認済み: `output/mirror_probe_bathrooms.png`）
- したがって **Mirror3D (CVPR 2021) の補正 GT が必須**。無いと測定自体が成立しない
- COCO に "mirror" クラスは無く、既存 YOLOv8-seg では検出不可

## C. 深度基盤モデルを使った鏡セグメンテーション

- B を反転: 「鏡を直す」ではなく **「深度/法線の挙動が異常だから鏡と分かる」**
- **指標は MSD / PMD の IoU・F値** → 壊れた深度 GT に依存しない（測定可能性の問題が消える）
- 異常信号の候補:
  - 壁の上では法線は一定のはずが、鏡の内側では**反射された部屋の法線**になり激しく変動
  - 深度が壁面の中で急に後退する
  - 意味的な重複（部屋の中にもう一つの部屋）
- 既存手法（MirrorNet の contextual contrast、PMD-Net）と原理は同じだが、
  **拡散型深度基盤モデルの予測/特徴を信号源にする点は比較的手薄**
- **注意**: 研究テーマが「深度推定の改善」から「鏡セグメンテーション」に変わる

## D. 高解像度データセット

- NYUv2 は 640×480 で、768 は既に拡大。**原画像に無い情報は生まれない**
- DIODE (1024×768) / ETH3D (6048×4032) は
  **本リポジトリが既に対応済み**（`datasets/eval/depth/configs/`）かつ Lotus の標準ベンチマーク
  → 「高解像度に移ると元手法と比較できない」という懸念は当たらない
- ただし**手法そのものは別途必要**。データを変えるだけでは新規性にならない

## E. 凍結 UNet + zero-init 側枝

- 学習開始時点で公式 Lotus と厳密一致 → **fine-tune 税が構造的にゼロ**
- しかし **Oracle 上限 19% は変わらない**。物体条件付けの天井は低いまま
- 単独では弱い。A や D と組み合わせる前提の技術要素

---

## 判断の規律（すべての案に共通）

これまでの失敗はすべて「測る前に作った」ことに起因する。着手順は固定:

1. **同一プロトコルでベースラインを取る**（`processing_res` を明示すること）
2. **Oracle 上限を測る** — 完璧な事前情報で指標がどれだけ動くか
3. **閾値を測定前に決める**（例: 上限 5% 未満なら破棄）
4. **対照実験を最初から同時に回す**（v6 / C2 の教訓）
5. 上限が十分大きい場合のみ手法設計へ

Phase 0 の道具はそのまま転用できる:
`eval_object_oracle_ceiling.py`（Oracle）/ `eval_error_decomposition.py`（空間分解）

---

## 推奨

**A（法線）または C（鏡セグメンテーション）。**

理由は同じで、**depth ベンチマークの指標設計から出られる**こと。
4 回続けて止まった原因はいずれも「指標が測らない量を扱っていた」ことにある。

- **A** は研究テーマの連続性を保てる（Lotus の別タスク、リポジトリ対応済み）
- **C** は測定可能性が最も高いが、テーマがセグメンテーションに変わる

いずれも次の一手は同じ: **データを入手し、ベースラインと Oracle 上限を測る。**
