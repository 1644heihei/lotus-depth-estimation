# Lotus 精度向上 計画案

作成: 2026-08-26
ブランチ: `feature/object-depth-aux-loss`

これまでの物体検出ベース手法（pre-depth fusion / object attention / object_bbox_loss）が
すべて失敗した原因を計測データから特定し、その上で「物体検出を活かしたまま」精度を
向上させるための計画をまとめる。

---

## 1. 新規に計測したベースライン（今回追加）

これまで **全実験の基準となる「公式 Lotus を同一プロトコルで評価した値」が存在しなかった**。
今回 654枚・同一プロトコル（`eval_regressor_predepth_nyuv2.py`, least-square disparity alignment,
processing_res=512, seed=42）で計測した。

`output/eval_baseline_official_654/`

| モデル | abs_rel | roi_abs_rel | bg_abs_rel | δ1 |
|--------|---------|-------------|------------|-----|
| **公式 Lotus（無改造）** | **0.05543** | **0.04475** | **0.05226** | **0.9698** |
| v5 step-250（全実験中の最良 fine-tune） | 0.05538 | 0.04476 | 0.05221 | 0.9697 |

## 2. 失敗の根本原因（4点、すべて計測で裏付け済み）

### 原因1: 前提が逆だった — Lotus は物体領域の方が既に得意

公式 Lotus のベースライン内訳:

| 指標 | 値 |
|------|-----|
| **roi_abs_rel（bbox 内）** | **0.04475** |
| **bg_abs_rel（bbox 外）** | **0.05226** |

物体数別の abs_rel:

| 画像内の検出物体数 | 枚数 | abs_rel | δ1 |
|--------------------|------|---------|-----|
| 0 個 | 132 | 0.05561 | 0.9664 |
| 1 個 | 249 | 0.05265 | 0.9724 |
| 2-3 個 | 195 | 0.05945 | 0.9655 |
| 4+ 個 | 78 | 0.05397 | **0.9779** |

**物体が多い画像で Lotus が苦戦している事実はない。** 4+ 個の画像はむしろ δ1 が最良（0.9779）。
そして bbox 内（0.0448）は bbox 外（0.0523）より **精度が高い**。

つまり「物体領域が弱点だから物体事前情報を注入する」という研究の出発点そのものが、
データに支持されていなかった。改善余地はむしろ背景（壁・床・天井・遠景）側にある。

> 注意: roi/bg はそれぞれ独立に least-square alignment を行った上での値のため、
> 領域サイズと深度レンジの違いにより厳密な等価比較ではない（物体は小さく深度レンジが狭いため
> 有利に出やすい）。ただし「物体領域が明確な弱点である」という主張を支持しない点は変わらない。

### 原因2: 注入している情報が本体より 6.8 倍不正確

| 予測器 | 対象 | abs_rel | δ1 |
|--------|------|---------|-----|
| **Lotus 本体** | NYUv2 深度 | **0.055** | **0.970** |
| object depth regressor v4_mask | NYUv2 物体深度 | **0.374** | 0.489 |
| object depth regressor v5_roi | Hypersim holdout | 0.256 | 0.552 |

（`output/object_depth_regressor_v4_mask/eval_nyuv2_test/summary.json`,
`output/object_depth_regressor_v5_roi/metrics_hypersim_holdout.json`）

regressor は NYUv2 で abs_rel=0.374、つまり **平均 37% ずれた深度**を出力する。これを
abs_rel=0.055 の本体に「事前知識」として渡している。事前知識ではなくノイズであり、
UNet が無視するように学習するのは合理的な挙動である（実際 attention ON/OFF は noop だった）。

### 原因3: 評価指標が絶対深度を洗い流す — 消える量を予測していた

- `evaluation/util/alignment.py::align_depth_least_square` は予測全体に **scale + shift を GT に fit** する
- さらに `utils/object_pre_depth_regressor.py::fit_relative_disparity_calibration` が
  regressor 予測 → Lotus 予測へ **もう一度 scale + shift を fit** する

regressor が出力する「この椅子は 2.3m」という絶対 metric 深度は、**二重の scale-shift fit で
完全に消える**。fit 後に残るのは物体間の相対順序・相対間隔のみで、それを regressor は bbox
サイズという極めて粗い手がかりから推定している。

**指標が測っていない量を予測する設計になっていた。**

### 原因4: セグメンテーションマスクを計算した上で捨てている

`utils/object_detection_cache.py::run_yolo_detections`（L153-163）は yolov8n-seg で
**ピクセル単位のマスクを計算している**が、JSON に保存されるのは以下のスカラー 6 個だけ:

```
mask_area, mask_fill_ratio, mask_axis_ratio,
mask_angle_sin2, mask_angle_cos2, mask_orientation_confidence, mask_valid
```

**空間マスクそのものは破棄される。** その結果、下流はすべて bbox 矩形で動いている:

```python
# utils/object_detection_cache.py::detections_to_mask
mask[y1:y2, x1:x2] = 1.0   # 矩形塗りつぶし
```

- pre-depth の貼り付け（`build_pre_depth_from_regressor`）は **矩形全体に定数深度を書き込む**
- 椅子・机の bbox 矩形の 30〜50% は背景（`mask_fill_ratio` がまさにその割合を示している）
- つまり事前情報の footprint の約半分は **空間的に誤った深度**を主張している

自前で持っている `mask_fill_ratio` が「その事前情報がどれだけ誤っているか」を表しているのに、
それを使わずに矩形を貼り続けていた。

### 補足: conditioning 自体は効いていた（がそれ以上に fine-tune が壊していた）

`output/eval_three_conditions_nyuv2/`（同一 9ch モデル内での比較, 654枚）:

| 条件 | abs_rel |
|------|---------|
| unconditioned（条件ゼロ埋め） | 0.07514 |
| **crop_predepth（Lotus 自身を物体 crop に再適用）** | **0.06038** |
| regressor_predepth（regressor 由来） | 0.06318 |

- モデルは条件入力を **確かに使っている**（0.0751 → 0.0604）
- そして **crop 方式（0.0604）が regressor 方式（0.0632）より良い**
  = 「Lotus 自身の予測」の方が「弱い regressor」より有用、という直接証拠
- しかし **どれも公式 Lotus（0.0554）に届かない**
  = conditioning の利得より fine-tune による劣化の方が大きい

（注: unconditioned の 0.0751 は条件付き学習したモデルにゼロを入れた OOD 値のため、
conditioning の純粋な利得の測定ではない。ただし crop > regressor の順位は有効。）

## 3. 方針転換の要点

物体検出は捨てない。ただし **役割を変える**。

| 従来（失敗） | 転換後 |
|--------------|--------|
| ❌ 物体の**絶対深度を予測して教える**<br>（本体より 6.8 倍不正確、しかも指標で消える） | ✅ **どこに物体境界があるか**教える<br>（Lotus が原理的に苦手、マスクは正確） |
| ❌ bbox 矩形に定数深度を貼る<br>（footprint の半分が背景） | ✅ **どこを高解像度で見直すべきか**教える<br>（crop 再推論、実測で最良） |
| ❌ UNet 本体を fine-tune する<br>（必ずベースより劣化する） | ✅ **どのピクセル群が同一物体か**教える<br>（平面性・順序の制約） |

検出器を「深度の情報源」ではなく **「空間的な注意の割り当て器 / 境界の教師」** として使う。

Lotus は VAE で 8 倍ダウンサンプルするため（512×512 → latent 64×64）、
**物体境界が原理的にボケる**。これは Lotus 本体の構造的弱点であり、
全解像度のセグメンテーションマスクが直接埋められる数少ない情報ギャップである。

## Phase 0: 計測基盤の整備と Go/No-Go 判定（最優先・1〜2日）

手法を試す前に「そもそも改善余地があるか」を確定させる。ここを飛ばしたことが
これまでの失敗の最大の要因である。

### 0-1. 公式 Lotus ベースライン ✅ 完了

`output/eval_baseline_official_654/` — abs_rel 0.05543 / δ1 0.9698。
**以後すべての実験でこの値を併記すること。**

### 0-2. Oracle 上限測定 ✅ 完了 — 結果は §4 参照

実装: `eval_object_oracle_ceiling.py` / 結果: `output/eval_object_oracle_ceiling/`

「完璧な物体情報があったら abs_rel はどこまで下がるか」を、公式 Lotus の予測を後処理して測定した。

| Oracle | 内容 | 何を測るか |
|--------|------|-----------|
| **A** | 各物体領域の**深度レベルのみ** GT に合わせる<br>（予測の形状は保持、距離だけ正解にする） | **完璧な regressor** が達成できる上限<br>＝ regressor 路線の理論的天井 |
| **B** | 各物体領域を **GT 深度で完全置換** | 物体領域を扱うあらゆる手法の上限 |
| **BG** | 逆に**物体以外**を GT で完全置換 | 誤差のうち背景側の取り分 |

各々を **bbox 矩形版 / seg マスク版**の両方で実施。alignment は置換の**前**に行う
（置換後だと GT が fit に漏れて循環参照になる）。

**判定基準（測定前に設定）:**

- Oracle A の改善が **5% 未満** → **regressor 路線は原理的に死んでいる。完全に破棄する。**
- Oracle B ≫ Oracle A → 改善余地は「物体の**形状・境界**」にある → Phase 1 へ進む
- Oracle B の改善も **15% 未満** → 物体条件付け路線全体を棚上げし、背景側 or 別方向へ

### 0-3. 誤差の空間分解

公式 Lotus の per-pixel 誤差を以下で分解し、**どこで間違えているか**を特定:

- 深度不連続の境界 ±k px / 物体内部 / 背景平面部 / 遠景（>5m）
- seg マスク境界 ±k px（Lotus のボケがここに集中しているかの検証）

Phase 1-1（境界リファインメント）が効くかどうかはこの結果で決まる。

### 0-4. 実験規律の整備

- validation ベスト checkpoint の**自動保存**（現状 `checkpoints_total_limit` でベストが消える。
  12k 学習ではベストの step-4500 が削除済み）
- 全評価スクリプトに公式ベースラインの併記を必須化
- **ablation 対照を最初から同時に走らせる**（v6 で得た教訓 — 対照なしの解釈は誤る）

## Phase 1: 学習なしで効く手法（低リスク・即効性）

**fine-tune を一切行わないため、公式 Lotus の性能を構造的に壊しようがない。**
ベースラインからの純増しか起こり得ないので、まずここで勝負する。

### 1-1. マスク誘導の境界リファインメント（training-free）

- Lotus は latent 64×64 のため深度境界が ~8px ボケる（VAE の構造的制約）
- YOLO-seg の**全解像度マスク**をガイドに、境界を後処理でシャープ化
  - joint bilateral filter / guided filter（マスクを guidance channel に）
  - あるいは境界近傍の各ピクセルを「マスクの内側/外側」に応じて再割り当て
- 学習ゼロ、数時間で検証可能
- **前提**: Phase 0-3 で境界誤差が有意な寄与を持つことが確認できた場合のみ実施

### 1-2. 物体 crop の高解像度 re-inference（training-free）

既存の `utils/object_pre_depth.py::CoreDepthPredictor.build_pre_depth`（L119-126）は
すでに「各物体 crop に Lotus を再適用」する実装を持っている。
これを **conditioning の材料ではなく最終出力の材料**として使う。

```
1. 全体画像に Lotus → 大域 disparity D_g
2. 各物体マスク M_i について crop を Lotus に再入力 → D_i
   （512×512 の latent 予算を小さな物体に集中させる = 実効解像度の向上）
3. D_i を M_i 周辺で D_g に scale+shift fit
4. マスク内のみソフトブレンド（矩形ではなくマスクを使う）
```

- 根拠: crop 方式は実測で regressor 方式に勝っている（0.0604 vs 0.0632）
- BoostingMonocularDepth / PatchFusion と同系統の確立された手法
- 学習不要のため fine-tune 税ゼロ

> Phase 1 で公式 Lotus を上回れれば、それ自体が研究成果として成立する
> （「学習不要の検出誘導リファインメント」）。

## Phase 2: 学習する場合（fine-tune 税をゼロにする構造）

Phase 0/1 の結果、学習が必要と判断した場合のみ。

### 2-1. UNet 完全凍結 + zero-init 側枝（ControlNet 型）

**これまで全 fine-tune がベースより劣化した問題を、構造的に解決する。**

- UNet 本体を**完全凍結**（現行の LoRA on to_q/k/v/out は本体をドリフトさせるため廃止）
- 条件経路を zero-init の側枝 / residual adapter として追加
- **学習開始時点で出力が公式 Lotus と厳密に一致することを保証**
- 学習は「ベースからの差分」のみを学ぶ → 悪化しない構造

これにより初めて「conditioning の純粋な寄与」が測定可能になる。

### 2-2. 条件入力の再設計

| 項目 | 変更 |
|------|------|
| regressor の絶対深度 | **廃止**（原因2・原因3より） |
| crop-based pre-depth | 採用（Lotus 自身＝精度は本体同等） |
| **seg マスクの空間チャンネル** | **新規追加**（現在破棄している情報。矩形をやめる） |
| `mask_fill_ratio` 等 | 事前情報の**信頼度マップ**として使用 |

`ObjectDetection` に RLE または polygon でマスクを保存するようキャッシュ形式を拡張する必要がある
（`utils/object_detection_cache.py`）。

### 2-3. scale 不変な損失（指標と学習目標を一致させる）

原因3 より、絶対深度の回帰は指標に現れない。least-square alignment 後に残る量を直接最適化する:

- 物体間の**相対順序損失**（ordinal loss）— 「A は B より手前」は alignment で消えない
- **境界での勾配損失** — 深度不連続の位置と鋭さ
- 物体内部の**平面性 / 連続性**制約

## 4. Phase 0-2 実施結果 — Oracle 上限測定

> 詳細な実施記録・再現コマンド・実装上の注意は [`phase0_findings.md`](phase0_findings.md) を参照。

実装 `eval_object_oracle_ceiling.py` / 出力 `output/eval_object_oracle_ceiling/` / NYUv2 654枚

**検証**: baseline が独立計測（`output/eval_baseline_official_654/`）の 0.05543 と完全一致。
また `B_bbox` の gain（0.01115）+ `BG` の gain（0.04428）= 0.05543 = baseline となり、
物体領域と背景が誤差を過不足なく分割していることを確認（計算の正しさの裏付け）。

**`processing_res=768`（公式デフォルト）での結果。** 括弧内は 512 での値。

| variant | abs_rel | δ1 | gain | gain% | 対象面積 |
|---------|---------|-----|------|-------|----------|
| baseline（公式 Lotus） | 0.05000 | 0.9711 | — | — | — |
| **Oracle A bbox**（完璧な regressor） | 0.04892 | 0.9713 | 0.00108 | **2.1%**（2.0%） | 21.3% |
| **Oracle A mask** | 0.04843 | 0.9719 | 0.00157 | **3.1%**（3.1%） | 14.9% |
| Oracle B bbox（物体を完全に GT 化） | 0.04041 | 0.9752 | 0.00959 | 19.2%（20.1%） | 21.3% |
| Oracle B mask | 0.04338 | 0.9738 | 0.00662 | 13.2%（13.6%） | 14.9% |
| **Oracle BG**（背景を完全に GT 化） | 0.00958 | 0.9963 | 0.04042 | **80.8%**（79.9%） | 78.7% |

**gain% は 512 と 768 でほぼ一致しており、以下の判定は解像度設定に対して頑健である。**

### 判定 1: regressor 路線は破棄（判定基準に該当）

**Oracle A = 2.0%（bbox）/ 3.1%（mask）で、事前に設定した 5% の閾値を下回った。**

物体ごとの深度を **完全に言い当てる regressor** があったとしても、abs_rel の改善は 2〜3% が上限。
現行 regressor の実測精度は NYUv2 で abs_rel=0.374（原因2）であり、上限の数分の一しか達成できない。
**regressor による物体深度の注入は、原理的に投資に見合わない。この路線は完全に破棄する。**

### 判定 2: 物体領域の余地は「深度レベル」ではなく「形状」にある

Oracle B bbox（20.1%）は Oracle A bbox（2.0%）の **10 倍**。
物体領域の改善余地 20 ポイントのうち、**18 ポイントは形状・境界**に由来し、
深度レベル（距離）に由来するのは 2 ポイントしかない。

→ 深度の値を教える手法（regressor / pre-depth の定数貼り付け）ではなく、
**解像度・境界を改善する手法**（Phase 1-1 / 1-2）が正しい方向であることが裏付けられた。

### 判定 3: 誤差は画像全体にほぼ均等に分布している（最も重要な発見）

gain% を対象面積で割った「単位面積あたりの誤差密度」:

| 領域 | 面積 | gain% | 誤差密度 |
|------|------|-------|----------|
| seg マスク内（物体そのもの） | 14.9% | 13.6% | **0.91** |
| bbox 内 | 21.3% | 20.1% | **0.94** |
| bbox 内のうちマスク外（＝矩形の余白） | 6.4% | 6.5% | **1.02** |
| 背景（bbox 外） | 78.7% | 79.9% | **1.02** |

**誤差密度はどの領域でもほぼ 1.0。物体領域が特別に悪いわけではない。**
物体は「誤差が集中した攻めどころ」ではなく、単に画素の 15〜21% を占め、
それに見合った 14〜20% の誤差を持っているだけだった。

つまり物体領域を**完璧にしても、その面積分の誤差しか回収できない**。
これが、あらゆる物体条件付け手法が失敗した最終的な理由である。

補足として、bbox 内のマスク外領域（矩形の余白, 密度 1.02）は背景（1.02）と同じ挙動を示す。
**矩形の余白は「物体の一部」ではなく背景そのもの**であり、そこに物体深度を貼る現行実装
（原因4）が誤りであることが定量的に確認された。

### 計画への反映

| 項目 | 判定前 | 判定後 |
|------|--------|--------|
| regressor 路線（Phase 2-2 の一部） | 廃止候補 | **確定的に破棄** |
| Phase 1-1 / 1-2（学習なし・形状改善） | 有望 | **唯一の有望路線として最優先** |
| Phase 2（学習を伴う条件付け） | 条件付きで実施 | **保留** — 上限 20% に対し fine-tune 税が 9%+ あり割に合わない |
| 新規: 全画面への高解像度化 | — | **追加**（下記） |

### 追加方針: 「物体だけ」の枠を外す

Phase 1-2（crop 再推論）が効くとすれば、その理由は「物体だから」ではなく
**「その領域を高解像度で見直したから」**である。実際、Lotus は 512×512 → latent 64×64 まで
ダウンサンプルするため、細部の欠落は画像全体で起きている。

判定 3 より誤差は全面に均等分布しているので、crop 再推論を **物体に限定せず画像全体へタイル状に
適用**すれば、20% の上限そのものを外せる（PatchFusion / BoostingMonocularDepth 系）。
物体検出はこの枠組みでも「どのタイルを優先するか / どこでブレンドするか」の
ガイドとして引き続き活用できる。

**先行検証**: `--processing_res` を上げるだけで baseline が改善するかを確認する
（解像度が本当にレバーなのかを 2 分で判定できる）→ §5 で実施、**大幅な改善を確認**。

## 5. processing_res スイープ結果 — 本命の発見

公式 Lotus（無改造・学習なし）で `--processing_res` のみを変えて NYUv2 654枚を評価した。
出力: `output/eval_baseline_official_654_res{640,768,896,1024}/`

| processing_res | latent 解像度 | abs_rel | δ1 | roi_abs_rel | bg_abs_rel | vs 512 |
|----------------|---------------|---------|-----|-------------|------------|--------|
| 512（従来の全実験） | 64² | 0.05543 | 0.9698 | 0.04475 | 0.05226 | — |
| 640 | 80² | 0.05123 | **0.9723** | 0.04069 | 0.04809 | **+7.6%** |
| **768** | 96² | **0.05000** | 0.9711 | **0.03818** | **0.04693** | **+9.8%** |
| 896 | 112² | 0.05574 | 0.9670 | 0.04144 | 0.05233 | −0.5% |
| 1024 | 128² | 0.06342 | 0.9599 | 0.04637 | 0.05964 | −14.4% |

### 発見 1: これは「新発見」ではなく **設定ミスの修正** だった

> [!IMPORTANT]
> **公式 Lotus のデフォルト `processing_res` は 768**（`pipeline.py:1041`, `eval.py:78`）。
> **この研究の全実験は非標準の 512 で走っていた。**
> 原因は regressor の ROI 抽出解像度（`train_object_depth_regressor.py:255`）が
> `eval_regressor_predepth_nyuv2.py:378-382` で拡散パイプラインの推論解像度に流用されたこと。
> 詳細は [`phase0_findings.md`](phase0_findings.md) §3.3.1。
>
> したがって **「公式 Lotus ベースライン 0.05543」自体が公式設定より劣化した値**であり、
> **過去の物体条件付け実験は、ハンデを負わせたベースラインと比較してなお負けていた。**

これまでの物体条件付けの全実験（LoRA 学習・attention・bbox loss・regressor、数ヶ月分）が
公式 Lotus を 1 度も上回れなかったのに対し、**設定を公式デフォルトに戻すだけで
abs_rel が 9.8% 改善した。学習は一切行っていない。**

さらに **roi_abs_rel の改善（−14.7%）が全体（−9.8%）より大きい**。
物体条件付けが狙っていた「物体領域のディテール改善」は、
**解像度を上げるだけで、しかもより大きく得られていた**。

Oracle B bbox の上限 20.1%（＝物体を完璧に GT 化した場合）の **約半分を、この 1 フラグで回収**している。

原因は構造的に明快で、Lotus は VAE で 8 倍ダウンサンプルするため
入力解像度がそのまま latent 解像度を決める（512→64², 768→96²）。
**物体条件付けで注入しようとしていた「ディテール」の正体は、単に潰れていた解像度だった。**

### 発見 2: 単純な解像度上げは 768 で頭打ち、それ以降は急落

曲線は 768 をピークとする明確な単峰形で、896 でベースライン同等、1024 で −14.4% と大きく悪化する。
モデルの学習解像度から離れすぎて **OOD（分布外）** になるためと考えられる。

**これはタイル分割推論（PatchFusion / BoostingMonocularDepth 系）が必要な理由そのものである。**
解像度を素朴に上げる方法には上限があるので、それを超えるには
**モデルが得意な解像度（512〜768）のタイルに分割して推論し、合成する**必要がある。

> [!NOTE]
> **テストセット調整の懸念は解消された。**
> 768 は公式 Lotus のデフォルト値であり、test 結果を見て選んだのではなく
> **公式の既定設定に戻しただけ**である。
>
> ただし「768 が最適」と主張する場合、そのスイープ自体は test 上で行っているため、
> validation で示す必要がある。「公式デフォルトを使った」と述べるだけなら問題ない。
>
> また **過去の全実験の数値は 512 で取得されている。** 実験群どうしの内部比較の
> 公平性は保たれているが、**公式 Lotus との比較としては過去の記録すべてが
> 公式に不利な条件だった**。再掲・引用時は必ず注記すること。

### 計画への反映（最終）

| 優先度 | 方針 | 根拠 |
|--------|------|------|
| **1** | **タイル分割による高解像度推論**（学習なし）<br>→ 実装計画: [`tiled_inference_plan.md`](tiled_inference_plan.md) | 発見 1・2。単純な解像度上げの上限を超える唯一の方法 |
| **2** | 物体検出を**タイルのガイド**として使う（配置・優先順位・ブレンド境界） | 判定 3 より物体は誤差の集中点ではないが、タイル制御の手がかりにはなる |
| **3** | マスク誘導の境界リファインメント（Phase 1-1） | 判定 2 より余地の 9 割は形状・境界 |
| — | ~~regressor による物体深度の注入~~ | **破棄**（判定 1: 完璧でも 2〜3% が上限） |
| — | ~~UNet を fine-tune する物体条件付け~~ | **保留**（fine-tune 税 9%+ が上限 19% を食い潰す） |
| **必須** | 全評価スクリプトの `--processing_res` を 768 に修正 | 発見 1。512 のまま比較すると公式に不利なハンデが残る |

以後のすべての評価は **`processing_res=768` を新しいベースライン（abs_rel 0.05000）**として比較すること。

## 実行順序とコスト・判断基準

| Phase | 内容 | コスト | リスク | 判断基準 |
|-------|------|--------|--------|----------|
| **0-1** | 公式ベースライン | ✅ 完了 | — | — |
| **0-2** | **Oracle 上限測定** | 半日 | なし | **Oracle A <5% → regressor 破棄**<br>**Oracle B <15% → 路線全体を棚上げ** |
| **0-3** | 誤差の空間分解 | 半日 | なし | 境界誤差が主要なら Phase 1-1 へ |
| **0-4** | 実験規律の整備 | 半日 | なし | — |
| **1-1** | 境界リファインメント | 1〜2日 | **なし**（学習不要） | baseline 0.05543 を上回るか |
| **1-2** | crop re-inference | 2〜3日 | **なし**（学習不要） | baseline 0.05543 を上回るか |
| **2-1** | 凍結 UNet + zero-init 側枝 | 1週 | 低（構造的に悪化しない） | baseline を上回るか |
| **2-2** | マスク条件の再設計 | 1週 | 中 | 2-1 との ablation で純寄与を測る |
| **3** | ScanNet 投入 | 1〜2週 | 中 | — |

> [!WARNING]
> **Phase 0-2（Oracle 上限測定）を最優先で実施すること。**
> これまでの失敗は「改善余地があるか確認せずに手法を作り込んだ」ことに起因する。
> Oracle が小さければ、どれだけ手法を工夫しても勝てない。逆に Oracle が大きければ、
> どこに余地があるか（オフセットか形状か）が判明し、手法の設計が一意に決まる。
